# Сигнал · Модус Трейд

MVP внутренних обращений сотрудников: проблемы, предложения, отзывы, назначения, SLA, уточнения, результат и подтверждение автора. React 18 / TypeScript / Vite; FastAPI / SQLAlchemy 2 / Alembic / Pydantic v2. SQLite по умолчанию, PostgreSQL через `DATABASE_URL`.

[Архитектура и права](docs/architecture.md) · [ТЗ этапа 2](docs/specs/02-backend.md) · [Отчёт этапа 2](docs/reports/02-backend.md).

## Быстрый запуск без Docker

Нужны Python 3.12+, uv, Node.js 22 и npm. Один раз установите frontend-зависимости: `cd frontend`, `npm install`.

Затем запустите две команды в двух терминалах из соответствующих каталогов:

```sh
# Терминал 1, каталог backend/
uv run python -m app
```

```sh
# Терминал 2, каталог frontend/
npm run dev
```

Первая команда автоматически установит Python-зависимости из lock-файла, применит миграции и загрузит сид только в пустую БД. Повторный запуск сохраняет изменения. API: `http://127.0.0.1:8000`, Swagger: `http://127.0.0.1:8000/docs`, интерфейс: адрес Vite, обычно `http://localhost:5173`. Vite проксирует `/api` на порт 8000.

Эквивалентный явный запуск по ТЗ, из `backend/`:

```sh
uv sync
uv run alembic upgrade head
uv run python -m app.seed --reset
uv run uvicorn app.main:app --reload
```

`--reset` удаляет предметные изменения и восстанавливает демо. В ограниченной Windows-среде агента `--reload` блокируется правами на named pipes; там используется обычный запуск без reload или `uv run python -m app`. В обычном окружении reload можно включить.

## Настройки

Примеры: `backend/.env.example`, `frontend/.env.example`. Для локального запуска файлы не обязательны. Настройки бэкенда:

| Переменная | По умолчанию / назначение |
| --- | --- |
| `DATABASE_URL` | `sqlite:///./signal.db`; для PostgreSQL — `postgresql+psycopg://user:password@host:5432/signal` |
| `JWT_SECRET` | Если не задан, случайный секрет процесса; для устойчивых сеансов задайте длинный случайный секрет в `.env` |
| `JWT_TTL_HOURS` | 12 часов |
| `BUSINESS_TIMEZONE` | Europe/Moscow |
| `SLA_INTERVAL_SECONDS` | 60 секунд, минимум 5 |
| `STORAGE_DIRECTORY` | `backend/storage/`, если запуск из `backend/` |
| `CORS_ORIGINS` | JSON-массив разрешённых origin; Vite работает через same-origin proxy |

Верхняя панель выполняет **демо-вход**: `POST /api/auth/demo-login` возвращает JWT, дальнейшие запросы используют Bearer-токен. Токен находится в памяти frontend, роль и права проверяет сервер. Это демонстрационный выбор личности; промышленный SSO через Битрикс24 / AD пока не реализован.

## HTTP и статический mock

HTTP включён по умолчанию: `VITE_API_MODE=http`. В БД сохраняются обращения, участники, история, уведомления, правила, отпуска и метаданные вложений; файлы хранятся отдельно на диске.

Статическая сборка без API:

```sh
# Bash, из frontend/
VITE_API_MODE=mock npm run build
npm run preview
```

В PowerShell:

```powershell
$env:VITE_API_MODE = 'mock'
npm run build
npm run preview
```

Для возврата к HTTP в PowerShell: `$env:VITE_API_MODE = 'http'`. Значение выбирается при старте dev-сервера или сборке, поэтому после изменения перезапустите Vite. Альтернатива — задать переменную в `frontend/.env.local`.

Mock получает тот же `data/seed.json`, сохраняет предметные изменения в localStorage `signal-demo-v3`. Реальный SLA-планировщик, уведомления и XLSX требуют HTTP; в mock загрузки доступны до перезагрузки страницы. HTTP-адаптер не читает предметные данные из localStorage. Все экраны используют один фасад `src/api/index.ts`.

## Сброс и календарь

Из `backend/`: `uv run python -m app.seed --reset`. В интерфейсе выберите администратора и нажмите «Сбросить демо-данные». Сброс включает 60 обращений и исходную оргструктуру. Он не удаляет старые физические файлы из storage; там могут остаться незакреплённые загрузки. SQLite-файл и storage не включаются в Git.

Источник данных один — `data/seed.json`; даты представлены смещениями в днях от момента загрузки. Есть девять укрупнённых категорий; исходные названия сохранены в `originalCategory`. Календарь РФ 2026–2027 — `backend/app/holidays.json`, включая переносы и рабочую субботу. SLA учитывает рабочие дни, длительность первого ответа — часы 09:00–17:00.

После сброса в компанейской аналитике 60 обращений, 60% с результатом и медиана первого ответа 12 рабочих часов. Фоновая проверка меняет старые реализованные обращения без реакции автора: они закрываются как подтверждённые по умолчанию, отдельно от явного подтверждения. Поэтому данные после запуска планировщика закономерно отличаются от снимка непосредственно после сброса.

## Демо по шагам

1. **Сотрудник → Сотрудник закупок.** Откройте «Новое обращение», выберите «Заявки и взаимодействие» и «Закупки». Введите: «В заявках на закупку часто нет назначения изделия и параметров, приходится уточнять у проектировщиков по несколько раз». Первым похожим будет A-001. У другого доступного сотрудника можно присоединиться к нему со своим контекстом; у самого автора кнопка ведёт в уже имеющееся обращение.
2. Отдельно создайте проблему с коротким заголовком или примите заголовок структуратора. Укажите потери времени, прикрепите txt/pdf/png-файл до 10 МБ. Внизу видны получатель и сроки. Отправьте и запомните ID вида `N-…`.
3. **Руководитель → Руководитель закупок.** Во входящих откройте новое обращение, возьмите в работу, запросите уточнение. Можно принять и отредактировать черновик ответа. У автора появится уведомление.
4. **Сотрудник → Сотрудник закупок.** Ответьте на вопрос в карточке. Снова выберите руководителя закупок, реализуйте обращение с конкретным «Что изменилось». Вернитесь к автору и нажмите «Проблема решена»: статус станет «Закрыто», улучшение появится в «Сделано». Перезагрузка сохраняет изменения в БД. Нажатие на файл скачивает его через проверяемый API.
5. Для возврата выберите «Не решена — вернуть» до подтверждения, укажите причину и посмотрите новый срок. В сиде уже есть S-017 и S-027 с возвратами. Для отказа откройте новое предложение, выберите «Отклонено» и содержательную мотивировку; A-017 показывает исходный пример отказа.
6. **Администратор → Пользователи и роли.** Отправьте руководителя закупок в отпуск. Новое обращение уйдёт резервному, указанному в «Маршрутизации». Если в отпуске также резервный, обращение всё равно получит руководителя подразделения или направления; причина будет в истории. После демонстрации верните доступность.
7. **Администратор → Маршрутизация → Проверить SLA сейчас.** Старые просрочки создадут события и уведомления, решения с просрочкой больше трёх рабочих дней получат метку «Эскалировано». Повторный запуск не дублирует одно напоминание. Старые реализации без ответа автора закроются по умолчанию. Уведомления доставляются в колокольчик; email и Битрикс24 только имитируются логом.
8. **Руководитель → Руководитель направления (`manager-2`).** Только у него включена компанейская аналитика. Другие ответственные видят свою область. Нажмите кластер, ячейку матрицы или подразделение SLA — детализация придёт отдельным API-запросом. «Выгрузить в Excel» скачает реестр за выбранный период. Метрика подтверждений по умолчанию показана отдельно от подтверждений авторов.

Прямой запрос к чужой полной карточке под токеном сотрудника возвращает 403, если он не автор и не участник. Администратору полная карточка и вложения недоступны; «Сделано» — отдельное публичное представление. В демо-переключателе можно явно войти под другим пользователем, поэтому для проверки прав используйте конкретный выданный токен.

## Проверки

Из `backend/`:

```sh
uv run pytest
```

Ровно 12 тестов ключевой доменной логики: переходы, обязательные пояснения, права, резервные назначения и календарь. Тестов эндпоинтов, frontend, e2e и smoke-скриптов нет.

Из `frontend/`:

```sh
npm run build
npx tsc --noEmit
npm run format
```

## Docker — целевое развёртывание

`docker-compose.yml`: PostgreSQL 17, backend и frontend через nginx, отдельные тома БД и вложений. Задайте `POSTGRES_PASSWORD` и `JWT_SECRET` в окружении или корневом `.env`, затем `docker compose up --build`. Пароль в URL должен быть URL-safe либо корректно закодирован. Интерфейс будет на `http://localhost:8080`, Swagger — `/docs`.

**Docker и PostgreSQL не проверены запуском в среде агента.** SQLite-путь с миграциями, сидом и живым API проверен. Контейнер backend применяет миграции и загружает сид только в пустую БД; существующие данные не сбрасываются.

## Код

- `backend/app/domain/` — workflow, права, маршрутизация, календарь.
- `backend/app/models.py`, `migrations/` — typed ORM и схема БД.
- `backend/app/services.py`, `sla.py` — транзакционные операции и сроки.
- `backend/app/ai/provider.py` — интерфейс AIProvider и детерминированная реализация.
- `backend/app/storage.py`, `notifier.py` — заменяемые адаптеры файлов и внешних уведомлений.
- `backend/app/analytics.py` — SQL-агрегаты и Excel.
- `data/seed.json` — единственный демо-набор для обоих режимов.
- `frontend/src/api/http/`, `mock/` — адаптеры за прежними сигнатурами фасада.

Ограничения и план интеграций с Битрикс24, AD и 1С — в [архитектуре](docs/architecture.md). Реальные LLM и интеграции относятся к следующим этапам.

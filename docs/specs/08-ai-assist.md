# ТЗ для Codex · Этап 8 · Три ИИ-помощника, которые снимают ручную работу

## Контекст
Генеративный слой уже есть (`backend/app/ai/llm.py`, `GeminiProvider`): вызовы Gemini по кнопке, JSON-схемы и валидация ответа (`response_schema`, `_validate`), кеш `llm_cache`, дневной лимит и учёт токенов (`_reserve`, `llm_usage`), маскировка персональных данных (`mask_personal_data`), тихий возврат к правилам при любой ошибке. Локальный смысловой поиск — `backend/app/ai/embeddings.py`, кластеры — `backend/app/ai/clusters.py`. Подпись источника в интерфейсе — `frontend/src/components/AiSource.tsx`.

Цель этапа — три функции, каждая убирает конкретный кусок ручной работы. Все три **строятся на этих механизмах**: новых SDK, новых таблиц кеша и новых способов вызова не делать — только новые функции в `GeminiProvider` со своими схемами и версией промпта.

Бюджет Gemini на аккаунте около $3. Каждая функция — **один вызов по явному клику**, ответ кешируется. За весь этап разработки — **не больше 6 реальных вызовов** (по два на функцию). Отладку делай на кеше и на правилах.

## 1. Уточняющие вопросы до отправки (сотрудник)

**Зачем.** Сейчас расплывчатое обращение («с заявками всё плохо») уходит ответственному, тот запрашивает уточнение, автор отвечает через день. Если задать вопросы до отправки, обращение придёт сразу полным, и круг «Ожидает уточнения» не понадобится.

**Как работает.**
- В форме нового обращения, рядом с «Структурировать текст», кнопка **«Проверить полноту»**. Активна при тексте от 20 символов.
- Ответ — блок «Чего не хватает» с 1–3 короткими вопросами по сути текста, например: «На каком этапе это происходит — при подаче заявки или при согласовании?», «Как часто: каждую заявку или иногда?», «Есть ли пример — номер заявки или объекта?». Под каждым вопросом — поле для короткого ответа.
- Кнопка **«Добавить ответы в описание»** дописывает к тексту блок «Уточнения:» с парами «вопрос — ответ» (пустые пропускаются). Блок можно закрыть без изменений.
- Если текст уже полный, ответ — одна строка «Описание достаточно полное» без вопросов.
- Не блокировать отправку: это подсказка, а не обязательный шаг.

**LLM.** Вход: текст (маскированный), выбранные категория и подразделение. Выход JSON: `{"complete": bool, "questions": [string, ≤3]}`, каждый вопрос ≤ 140 символов, по-русски, без вопросов о том, что уже есть в тексте. В промпте — контекст компании (системы безопасности: СКУД, видеонаблюдение, ОПС; проектирование, закупки, ПНР, сервис). `maxOutputTokens` ~250.

**Без LLM (правила).** Проверить наличие трёх признаков: где/на каком этапе (слова «этап», «при», «когда», «на объекте», названия процессов), как часто («каждый», «часто», «раз в», «иногда», цифры), пример (цифры, номера, «например»). Для отсутствующих — шаблонные вопросы. Подпись «Автоподсказка по правилам».

**API.** `POST /api/ai/completeness` — сотрудник; тело `{text, category, targetDepartment}`; ответ `{complete, questions, source, cached}`.

## 2. Корневая причина кластера (руководитель)

**Зачем.** Главная идея продукта — управлять проблемами, а не обращениями. Сейчас кластер показывает 12 обращений и чел.-часы, но руководителю всё равно нужно читать их все, чтобы понять, в чём дело. Функция превращает 12 жалоб в одну причину и одно системное решение.

**Как работает.**
- В детализации кластера (открывается из таблицы «Повторяющиеся проблемы» и из треемапа на «Аналитике»), над списком обращений — блок **«Корневая причина»** с кнопкой «Определить».
- Ответ:
  - **Причина** — одно предложение («Нет владельца маршрута согласования: каждое подразделение считает, что пакет ведёт другое»);
  - **Системное решение** — одно-два предложения, что изменить в процессе, а не в отдельном обращении;
  - **На чём основано** — 2–4 ID обращений, которые лучше всего подтверждают вывод (ссылки на карточки);
  - **Что уже пробовали** — если в кластере есть реализованные обращения: кратко, что сделали и закрыло ли это проблему (подтверждено автором / возвращено).
- Доступно тем, кто видит аналитику (те же права, что у кластеров). Кешируется до изменения состава кластера.

**LLM.** Вход: название кластера, затронутые подразделения, суммарные чел.-часы, до 15 обращений кластера — **заголовок, первое предложение текста (маскированное), статус, «что изменилось» или причина отказа**. Без комментариев, без имён, без вложений. Выход JSON: `{"cause": string ≤ 220, "solution": string ≤ 320, "evidence": [ticketId, 2–4], "tried": string ≤ 260 | ""}`. Валидация: `evidence` — только ID из переданного списка, иначе отбросить лишние. `maxOutputTokens` ~400.

**Без LLM (правила).** Причина — «Повторяется в N обращениях из M подразделений», решение — «что изменилось» самого свежего подтверждённого реализованного обращения кластера, если есть, иначе «Назначить владельца проблемы и решить её системно». `evidence` — обращения с наибольшей «стоимостью».

**API.** `POST /api/analytics/clusters/{clusterId}/root-cause` — права как у аналитики; ответ `{cause, solution, evidence, tried, source, cached}`.

## 3. Подсказка решения из истории (ответственный)

**Зачем.** У ответственного нет под рукой опыта компании: как подобное уже решали. Поле «что изменилось» закрытых обращений — это готовая база решений. Функция показывает её в момент, когда нужно принять решение.

**Как работает.**
- В карточке обращения, в панели «Действия ответственного», над «Черновиком ответа» — блок **«Как решали похожее»** с кнопкой «Показать».
- Ответ:
  - до 3 похожих **уже реализованных** обращений — ID (ссылка), заголовок, «что изменилось», отметка «подтверждено автором» или «возвращено»;
  - **Рекомендация** одной-двумя фразами: что из этого применимо здесь и что стоит проверить;
  - если похожих решённых нет — «Похожих решённых обращений нет: это новая проблема» и предложение начать с запроса уточнения.
- Кнопка «Использовать в ответе» подставляет рекомендацию в поле «Комментарий к действию» (руководитель редактирует).
- Подбор похожих — **локальным поиском** (`embeddings`, только статусы «Реализовано» и «Закрыто», исключая само обращение); LLM пишет только рекомендацию. Если локальная модель недоступна — лексический поиск из `provider.py`.

**LLM.** Вход: заголовок и текст текущего обращения (маскированные), категория, до 3 найденных решённых обращений (заголовок, «что изменилось», подтверждено/возвращено). Выход JSON: `{"recommendation": string ≤ 360}`. `maxOutputTokens` ~250.

**Без LLM (правила).** Похожие показываются так же (это не LLM), рекомендация — «Похожий случай X решили так: <что изменилось>. Проверьте, применимо ли здесь».

**API.** `POST /api/tickets/{ticketId}/solution-hints` — только тот, кто может управлять обращением (`can_manage`); ответ `{similar: [...], recommendation, source, cached}`.

## Общие требования
- Для каждой функции — своя `function`-метка в кеше и учёте токенов, своя версия промпта, свой лимит выходных токенов. `GET /api/ai/status` продолжает показывать суммарный расход.
- Маскировка `mask_personal_data` — на всё, что уходит в Gemini.
- Подпись источника — существующий `AiSource`: «Сформировано Gemini (внешний сервис) · проверьте перед сохранением» или «Автоподсказка по правилам».
- Состояния блоков: пусто (кнопка), загрузка, результат, ошибка или лимит (результат правил + короткое пояснение).
- Визуальный стиль — как во всём приложении после этапа 7 (палитра, типографика, панели). Без иконок-искорок.
- Mock-режим: все три функции работают на правилах.
- `docs/architecture.md`, раздел «AI-слой»: добавить три функции в таблицу — что делает, что уходит во внешний сервис, где видно.
- `docs/roles-guide.md` — **не трогать**, оркестратор обновит сам.

## Тесты — строгое ограничение
Не больше **2** новых pytest, без сети и без реальных вызовов Gemini:
- правила полноты находят отсутствующие признаки («где», «как часто», «пример») и не задают вопросов на полном тексте;
- валидация корневой причины отбрасывает `evidence`, которых нет в переданном списке.

Никаких тестов фронтенда, e2e, smoke-скриптов, харнессов и тестов для тестов.

## Не делать
- Чат, стриминг, агентов, фоновые вызовы LLM, вызовы при загрузке страницы.
- Новые таблицы для кеша или учёта (использовать существующие).
- Изменения в других экранах сверх описанного.
- Коммиты — оркестратор проверит и закоммитит сам.

## Готово, когда
- [ ] «Проверить полноту» на расплывчатом тексте задаёт 1–3 предметных вопроса, ответы дописываются в описание; на полном тексте вопросов нет.
- [ ] «Корневая причина» в детализации кластера даёт причину, системное решение, ссылки-доказательства и «что уже пробовали».
- [ ] «Как решали похожее» в карточке показывает до 3 реализованных похожих обращений с результатом и рекомендацию; «Использовать в ответе» подставляет текст.
- [ ] Без ключа (`LLM_PROVIDER=none`) все три функции работают на правилах без ошибок; повторный клик берётся из кеша.
- [ ] `uv run pytest` — все зелёные (не больше 21), `npm run build` и `npm run build:mock` проходят.
- [ ] Отчёт `docs/reports/08-ai-assist.md`: что сделано, сколько реальных вызовов и токенов потрачено, по одному примеру ответа на функцию, ограничения.

# ТЗ для Codex · Этап 2 · Бэкенд и реальная логика «Сигнал»

## 0. Контекст
- `docs/concept.md`: концепция и изюминки.
- `docs/specs/01-ui-prototype.md`, `docs/specs/01.1-prototype-polish.md` и отчёты в `docs/reports/`: что уже сделано во фронтенде.
- Фронтенд (`frontend/`) работает на мок-слое `frontend/src/api/`. Все экраны ходят только через него, типы лежат в `frontend/src/types.ts`.

## 1. Цель этапа
Заменить мок-слой реальным сервером: данные в БД, права проверяются на сервере, маршрутизация, SLA, эскалации, история, уведомления и вложения работают по-настоящему. Фронтенд остаётся визуально тем же, меняется только источник данных. AI-функции (похожие, структуратор, черновики) на этом этапе переносятся на сервер **в текущем детерминированном виде** за отдельным интерфейсом. Реальная LLM будет на этапе 3.

Работающий MVP оценивается выше прототипа, поэтому всё из раздела 6 должно реально проходить через API.

## 2. Стек (фиксированный)
- `backend/`: Python 3.12+, FastAPI, SQLAlchemy 2 (typed ORM), Alembic, Pydantic v2. Зависимости через `uv` (`pyproject.toml` + `uv.lock`).
- БД: **SQLite по умолчанию** (запуск без Docker одной командой) и **PostgreSQL как целевая СУБД** (через `DATABASE_URL`). Код не должен содержать SQLite-специфики. Миграции Alembic должны работать на обеих БД.
- Фоновые задачи (SLA, эскалации): простой планировщик внутри процесса (APScheduler или asyncio-цикл, интервал настраивается) плюс эндпоинт ручного запуска для демо.
- Вложения: локальное файловое хранилище `backend/storage/` за интерфейсом `Storage`, чтобы потом подменить на S3-совместимое. Ограничения: 10 МБ, белый список расширений (pdf, png, jpg, docx, xlsx, txt).
- `docker-compose.yml` в корне (postgres + backend + frontend через nginx) — как целевой вариант развёртывания. Docker в среде агента недоступен, поэтому compose нужно написать аккуратно, а в отчёте пометить как непроверенный.

## 3. Модель данных
Таблицы (имена условные): `users`, `departments`, `categories`, `routing_rules`, `tickets`, `ticket_participants` (присоединившиеся с контекстом и оценкой потерь), `comments`, `ticket_events` (журнал аудита: кто, когда, что изменил — старое и новое значение статуса или ответственного), `attachments`, `notifications`, `clusters`, `ticket_clusters`.
- Статусы и переходы — **явная машина состояний** в одном модуле (`domain/workflow.py`): разрешённые переходы, кто может их выполнять, обязательные поля (мотивировка отказа, «что изменилось», текст запроса уточнения). Недопустимый переход → 409 с понятным сообщением на русском.
- Сроки: SLA первого ответа и решения в **рабочих днях**, с производственным календарём РФ в виде простого списка праздников в конфиге (2026–2027).
- **Источник сида — один.** Вынеси демо-данные в `data/seed.json`, даты — как смещения в днях относительно момента загрузки. Из этого файла загружаются и бэкенд (`uv run python -m app.seed --reset`), и мок-режим фронтенда. Текущие данные фронтенда после этапа 1.1 переносятся без потерь: A-001…A-020 и переписанные S-001…S-040.

## 4. Доступ и аутентификация
- Демо-вход: `POST /api/auth/demo-login {userId}` возвращает подписанный токен (JWT, HS256, секрет из env). Переключатель роли во фронтенде теперь вызывает этот вход. В UI нужно явно подписать: «Демо-вход. В промышленной версии — SSO через Битрикс24 / AD».
- **Права проверяются на сервере** (зависимости FastAPI, единый модуль `domain/permissions.py`):
  - Сотрудник видит свои обращения и те, к которым присоединился, плюс публичные представления «Похожие» (без чужих комментариев) и «Сделано».
  - Ответственный видит назначенные ему.
  - Руководитель видит обращения своего подразделения и аналитику. Компанейскую аналитику видит только роль с флагом `can_view_company_analytics` (в демо — у одного руководителя).
  - Администратор видит справочники, правила и пользователей. **Содержимое обращений администратору не показывать** (разделение обязанностей), только агрегаты.
- Анонимный «конверт» на этом этапе **не делать**: только заложить nullable `author_id` и флаг `is_anonymous` в модели и описать подход в `docs/architecture.md`.

## 5. Логика
- **Маршрутизация:** правило «категория + подразделение» → правило категории → правило по умолчанию. Если основной ответственный в отпуске — резервный. Если недоступны оба — назначается руководитель подразделения проблемы, и в журнал пишется событие «назначено по резервному правилу». Обращение **никогда** не остаётся без ответственного.
- **SLA и эскалации** (часть изюминки «обращение не потеряется»):
  - за 1 рабочий день до срока — уведомление ответственному;
  - при просрочке первого ответа — уведомление руководителю подразделения и событие в журнале;
  - при просрочке решения больше чем на 3 рабочих дня — эскалация на уровень выше (руководитель направления), метка «Эскалировано» в карточке и во «Входящих».
- **Уведомления:** таблица `notifications` и колокольчик в верхней панели фронтенда со счётчиком непрочитанных и списком (клик открывает обращение). Каналы email и Битрикс24 — интерфейс `Notifier` с реализацией `LogNotifier` (пишет в лог, что было бы отправлено), без реальной отправки.
- **Закрытая петля:** «Реализовано» требует «что изменилось». Автор подтверждает решение или возвращает обращение («Возвращено автором», новый срок). Если автор не ответил за 5 рабочих дней — автоматическое закрытие с пометкой «подтверждено по умолчанию» (учитывается отдельно в метрике).
- **Похожие, структуратор, черновики:** переносятся на сервер как есть, за интерфейсом `AIProvider` (`ai/provider.py`) с реализацией `RuleBasedProvider`. Этап 3 добавит `LLMProvider`, поэтому интерфейс сразу должен принимать нужный контекст (текст, категория, подразделение, список кандидатов).
- **Аналитика** считается на сервере SQL-запросами и агрегациями, а не выгрузкой всех обращений на клиент. Эндпоинты отдают готовые KPI, распределения, кластеры, матрицу трения и SLA.
- **Экспорт:** `GET /api/analytics/export.xlsx` (openpyxl) — реестр обращений за период для руководителя. Это мелочь, но жюри любит «выгрузить в Excel».

## 6. Фронтенд
- `frontend/src/api/` получает два адаптера: `http` (по умолчанию) и `mock` (текущий, из `data/seed.json`). Выбор через `VITE_API_MODE`. Сигнатуры функций для экранов не меняются: экраны не должны знать, какой адаптер работает. Mock-режим нужен, чтобы прототип можно было показать статикой без сервера.
- Vite proxy: `/api` → `http://localhost:8000`.
- Добавить: колокольчик уведомлений, метку «Эскалировано», реальную загрузку и скачивание вложений, кнопку «Выгрузить в Excel» на аналитике.
- Ошибки API (403, 409, 422) показываются аккуратными сообщениями на русском, не stack trace.
- Визуальный стиль не менять (см. раздел 3 ТЗ этапа 1).

## 8. Тесты — строгое ограничение
Писать **только pytest-тесты на ключевую доменную логику**, всего **не больше 12 тестов**:
- машина состояний (запрещённый переход, обязательная мотивировка);
- права (сотрудник не видит чужое обращение; администратор не видит содержимое);
- маршрутизация с резервом и «никогда без ответственного»;
- расчёт рабочих дней с праздником.

**Не писать:** тесты фронтенда, e2e, тесты на каждый эндпоинт, тесты для тестов, фикстуры-фабрики сверх необходимого, smoke-скрипты, отдельные харнессы, тесты сидов.

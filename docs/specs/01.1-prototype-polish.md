# ТЗ для Codex · Этап 1.1 · Доработка прототипа по итогам приёмки

Контекст: этап 1 (`docs/specs/01-ui-prototype.md`, отчёт `docs/reports/01-ui-prototype.md`) принят оркестратором в браузере. Экраны и сценарии работают, стиль соответствует требованиям. Ниже перечислено, что мешает показывать прототип жюри. Объём ограничен этими пунктами: не добавляй новых экранов и функций сверх описанного.

## 1. Читаемость кода — приоритет №1
Сейчас код фактически минифицирован: 88 строк длиннее 300 символов, максимум 2756 символов (`api/index.ts`, `data/seed.ts`, `pages/*`). Жюри будет смотреть репозиторий, а на этапе 2 по этому коду будет строиться бэкенд.
- Добавь Prettier (`printWidth: 100`, одинарные кавычки, точки с запятой) и скрипт `npm run format`. Отформатируй весь `src/`.
- Разбей крупные файлы по смыслу:
  - `api/` → `tickets.ts`, `analytics.ts`, `routing.ts`, `ai.ts` (имитация AI: похожие, структуратор, черновики), `storage.ts`;
  - `pages/` → компоненты экрана в отдельных файлах там, где файл длиннее ~250 строк;
  - `components/ui.tsx` → отдельные компоненты (`Badge`, `Button`, `Modal`, `Table` и т.п.).
- Не создавать абстракции ради абстракций. Цель — чтобы человек мог открыть файл и прочитать его.
- Поведение после рефакторинга не должно меняться (кроме пунктов ниже).

## 2. Синтетические данные выглядят сгенерированными
Сейчас встречаются заголовки вида «Обязательные поля складской заявки · подготовка / передача / проверка / приёмка», а у всех реализованных улучшений одинаковый результат «Введён единый шаблон и определён владелец процесса».

Перепиши S-001…S-040 **вручную, без шаблонов и генерации из комбинаций**:
- каждое обращение — уникальная, конкретная рабочая ситуация, своими словами, 1–3 предложения, разная длина и стиль (кто-то пишет сухо, кто-то подробно);
- тематика — специфика компании из отрасли систем безопасности: спецификации на СКУД, видеонаблюдение и ОПС; замены оборудования аналогами; комплектация объекта; выезды на ПНР и сервис; передача объекта в эксплуатацию; склад, резерв и отгрузки; КП и тендерная документация; согласование договоров и приложений; документы закрытия; карточки номенклатуры; обучение новым линейкам; заявки в IT; повторный ввод данных между учётной системой и CRM (без названий реальных систем в тексте обращений);
- кластеры повторяющихся проблем должны складываться из **разных формулировок одной проблемы** — так, как это пишут разные люди, а не одной фразы с суффиксами;
- результаты («Что изменилось») у каждого реализованного — свои и конкретные (например: «В форму заявки добавлены обязательные поля „назначение“ и „аналог допустим да/нет“; возвраты заявок за 3 недели снизились с 9 до 2»);
- мотивированные отказы — разные, реалистичные причины;
- комментарии в истории — живые деловые реплики, а не однотипные фразы;
- никаких реальных имён людей, контрагентов, сделок — только роли.
Оригиналы A-001…A-020 не трогать (только при необходимости добавь им короткий заголовок, см. п. 3).

## 3. Заголовок обращения
Сейчас заголовок — обрезанный текст, он рвётся посреди слова («…у проектировщико»).
- Добавь в форму необязательное поле «Кратко о сути» (до 80 символов).
- Структуратор предлагает заголовок вместе с остальными полями.
- Если заголовок не задан, сформируй его из первого предложения с обрезкой **по границе слова** и многоточием.
- Длинные заголовки в таблицах обрезать визуально (ellipsis + title-подсказка), в карточке показывать полностью.

## 4. Поиск похожих ранжирует неточно
Текст «В заявках на закупку часто нет назначения изделия и параметров, приходится уточнять у проектировщиков по несколько раз» должен выдавать **A-001 первым** (сейчас первыми идут складские заявки).
Улучши детерминированный скоринг в `api/ai.ts`:
- стоп-слова, нормализация словоформ (простое усечение окончаний);
- взвешивание: совпадение в заголовке > в тексте; редкие слова весят больше частых (простой IDF по корпусу);
- бонус за совпадение категории или подразделения проблемы, если они уже выбраны в форме;
- показывать в карточке похожего короткое объяснение совпадения (например, «Совпадение: заявка, назначение, параметры»), сдержанно, мелким текстом.
Проверь руками ещё 2–3 своих примера на разные кластеры и запиши их в отчёт (как текст → кто вышел первым).

## 5. Метрики должны выглядеть правдоподобно
Сейчас 39 просроченных из 60 и 24,6% обращений с результатом — система выглядит провальной. Нужна картина «система работает, есть отдельные проблемные зоны». Ориентиры для периода 90 дней:
- просрочено решение — 10–15% открытых обращений;
- медиана до первого ответа — 6–20 рабочих часов;
- результат зафиксирован — 55–70%;
- подтверждено авторами — заметная часть реализованных, 1–2 возврата «не решено» (для демонстрации петли).

Сделай 1–2 подразделения заметно хуже остальных по SLA (например, IT-разработка и Проектирование): это даёт сюжет для демо. Распредели даты так, чтобы на недельном графике была видимая динамика: рост подачи после запуска, затем рост реализованных.

## 6. Аналитика — визуальная доработка
- «По категориям»: показывать топ-7 + «Прочие (N)» с раскрытием по клику.
- Недельный график: высота не меньше 240 px, читаемые подписи осей (≥ 11 px), ось Y с 3–4 делениями, подсказка при наведении на столбец.
- Проверить, что экран аналитики выглядит аккуратно при ширине контентной области 1100–1700 px.

## 7. Тесты — ограничение
Тесты **не писать**: ни юнит-, ни e2e, ни smoke-скриптов, ни харнессов. Проверка готовности — `npm run build`, `tsc --noEmit`, `npm run format` без изменений после повторного запуска.

# Этап 8 · Три ИИ-помощника

## Реализовано

- **Проверка полноты** рядом со структуратором в форме сотрудника. От 20 символов, по кнопке: до трёх вопросов с короткими необязательными ответами либо «Описание достаточно полное». Добавляются только заполненные пары в блок «Уточнения:»; закрытие ничего не меняет. Проверка не блокирует отправку, устаревший ответ при изменении текста/категории/подразделения игнорируется; превышение 6000 символов при добавлении объясняется без потери текста.
- **Корневая причина** над списком в детализации кластера из таблицы, treemap и ссылки `?cluster=`. Причина, системное решение, 2–4 ссылки-доказательства (одна, если в кластере одно обращение), прежние попытки с проверкой автором. Анализирует всю доступную историю кластера. Область доступа совпадает с аналитикой; ключ учитывает ID/версии всех доступных участников кластера, включая обращения вне 15 источников промпта. Известные имена удаляются. Если Gemini пропустил отметку подтверждения в прежней попытке, используется факт из карточки.
- **Как решали похожее** в действиях ответственного над черновиком. Локальный смысловой поиск до трёх обращений в статусах «Реализовано»/«Закрыто» с датой реализации и результатом, исключая текущее; при недоступной модели — лексическое ранжирование. Показаны результат и подтверждение/возврат/отсутствие явного подтверждения. Gemini пишет только рекомендацию, кнопка подставляет её в редактируемое поле действия. При отсутствии аналогов — предложение запросить уточнение, без внешнего вызова.
- Новые POST API: `/api/ai/completeness`, `/api/analytics/clusters/{id}/root-cause`, `/api/tickets/{id}/solution-hints`. Проверки роли сотрудника, области аналитики и `can_manage` выполняются сервером.
- Использованы существующие `GeminiProvider`, транспорт, маскировка, JSON-схемы, валидация, дневной лимит, `llm_cache` и `llm_usage`. У функций отдельные метки/версии промпта и лимиты 250/400/250 выходных токенов. Посторонние и повторные ID доказательств отбрасываются; недостаток допустимых доказательств приводит к правилам. Новых SDK и таблиц нет.
- В существующую `llm_usage` миграцией `b731e52a8010` добавлена JSON-разбивка по функциям. `/api/ai/status` сохраняет общие суммы и дополнительно показывает `functionsToday`. Старые ключи кеша сохранены. Правила новых помощников тоже кешируются: отключённый LLM отдельно, ошибка/лимит — на день UTC. Повторный клик не расходует попытку; кеш отключённого режима не мешает включить Gemini.
- Все блоки используют `AiSource`, состояния кнопки/загрузки/результата/ошибки и пояснение возврата к правилам. Mock реализует все три функции локально с кешем в памяти страницы. Внешних вызовов при загрузке страниц или вводе текста нет. Обновлён AI-раздел архитектуры.

## Проверки

- Добавлены ровно **2 pytest без сети**: признаки полноты/полное описание и фильтрация доказательств корневой причины. Существующие тесты не менялись. Итог: **21 passed** (`uv run pytest`, локальный `UV_CACHE_DIR`).
- `npm run build` — успешно, включая `tsc --noEmit`.
- `npm run build:mock` — TypeScript прошёл; Vite остановлен средой до загрузки конфигурации: esbuild `spawn EPERM`. Конфигурация проекта для обхода ограничения не менялась.
- Миграция применена к локальной БД. Ручные запросы действующего API с `LLM_PROVIDER=none`: все три функции вернули `source=rules`, повторные — `cached=true`; полный текст вернул `complete=true, questions=[]`. Сотрудник получил 403 для корневой причины и подсказки решения.
- По одному реальному запросу каждой функции вернули `source=llm`. Повторы всех трёх дали `cached=true`, расход не вырос. После перезапуска кеш сохранился. Для проверки установлен локальный лимит 3 попытки; постоянные настройки `.env` не менялись. Проверочный сервер остановлен.

## Примеры

**Полнота**, текст «С заявками всё плохо и это мешает работе», Gemini:

> На каком этапе работы возникают проблемы с заявками?
> Приведите конкретный пример сбоя при обработке заявок.

`complete=false`. Правила на этом же тексте дают три вопроса: где/на каком этапе, как часто и конкретный пример; на «На объекте при закупке каждый раз теряются параметры, например заявка 42» вопросов нет.

**Корневая причина**, кластер закупок, Gemini:

> Отсутствие единого регламентированного шаблона исходных данных и обязательных полей спецификации для инженерных систем на этапе инициации закупок.

Решение: «Внедрить обязательную верификацию полноты исходных параметров (назначение, исполнение, допустимость аналогов) в шаблонах заявок до их передачи в отдел закупок». Доказательства: `S-019`, `S-003`, `S-014`, `S-001`. В прежних попытках показан результат `S-040` (лист готовности комплекта) с отметкой «подтверждено автором» из карточки.

**Подсказка решения**, `A-001`, локально найдены `S-028` и `S-019` с результатами и подтверждением авторов. Рекомендация Gemini:

> Примените опыт внедрения листа недостающих исходных данных из аналогичного случая S-019. Необходимо проверить полноту указания назначения и параметров оборудования перед передачей заявки в закупки.

## Ограничения

- Mock-сборку нужно повторить вне ограниченной среды из-за `spawn EPERM`. Визуальная приёмка блоков в браузере здесь не выполнялась; e2e, smoke-скрипты и фронтенд-тесты не создавались.
- Корневая причина — гипотеза по максимум 15 источникам, не доказанная причинность. Правила дают счётчики и последний подтверждённый результат, а не семантический вывод. Аналоги не означают, что текущее обращение уже решено; автоматическое закрытие не выдаётся за подтверждение автором.
- Прежние ограничения маскировки регулярными выражениями и расчёт на один процесс сохранены. Исторические токены до новой миграции не разбиваются по функциям задним числом. После перезагрузки mock-страницы его кеш начинается заново.
- `docs/roles-guide.md` не изменялся. Коммитов нет.


## Приёмка оркестратором
Все три функции проверены в браузере с реальным Gemini: полнота задала три предметных вопроса, ответ дописался в описание; корневая причина для «Непрозрачного согласования документов» дала причину, решение, ссылки S-038, S-032, S-016 и «что уже пробовали»; подсказки для A-003 показали три реализованных обращения и рекомендацию.

Известное ограничение: для A-003 «Разные обозначения одного изделия» самое близкое по сути решение S-002 «Одинаковые камеры под разными артикулами» не попадает в тройку — лёгкая модель эмбеддингов даёт ему близость ниже 0,49. Улучшение: гибридный скоринг (смысл + совпадение основ слов) или более сильная многоязычная модель.

# Этап 6 · Получатель, видимость и администратор

## Что изменено

- Переключатель роли запоминает последнего выбранного пользователя каждой роли в localStorage `signal-role-users`. Начальные значения: сотрудник `employee-1`, руководитель `manager-1`, администратор `admin`. Сохраняется также выбор через демо-переход к получателю.
- При выборе категории подразделение основного ответственного подставляется через `GET /api/routing/preview` без `targetDepartment`. После ручного изменения подразделения автоподстановка его не перезаписывает. Блок «Получатель» размещён сразу под категорией/подразделением: имя, роль, подразделение, сроки и резервное назначение. Можно выбрать другого доступного руководителя либо вернуть назначение по правилу. Нижний блок использует тот же выбор; устаревший ответ preview не позволяет отправить форму с предыдущим маршрутом.
- `TicketDraft.assigneeId` необязателен. Сервер проверяет существование получателя, роль руководителя и отпуск (422), сохраняет сроки правила категории, назначает выбранного пользователя и уведомляет его. Событие журнала: «Получатель выбран автором: … (по правилу — …)». Без переопределения сохранена прежняя маршрутизация.
- После регистрации имя получателя показано в карточке и тосте. В обоих местах есть действие «Открыть как …», которое меняет демо-пользователя и открывает карточку с возвратом во «Входящие». Действие доступно только при `catalog.demoMode`.
- Руководитель подразделения дополнительно читает обращения авторов из своего подразделения, направленные в другие отделы. Во «Входящих» появилась отдельная вкладка «От моих сотрудников». `can_manage` не расширен: внешние назначения доступны без решений, переназначения и формы комментария; сервер тоже запрещает эти действия.
- Администратор получает весь реестр «Все обращения», полные карточки с обсуждением, историей, участниками и вложениями, аналитику компании, Excel, сводку, зарождающиеся проблемы и локальный поиск. Может переназначать открытые обращения с записью в журнал. Статусы, отказ, реализация и черновик решения ему недоступны; в карточке показана только форма переназначения. Из аналитики открывает карточку без смены роли.
- Mock использует общий с UI помощник прав, повторяет чтение/ограничения, выбор получателя, проверку отпуска, журнал и аналитику администратора. Матрица доступа на экране пользователей, README, архитектура и pitch обновлены. CSS и визуальный стиль не менялись.

Изменён только один существующий тест: администратор видит обращение, посторонний сотрудник — нет. Добавлен только один тест: руководитель подразделения читает обращение своего сотрудника с внешним назначением и не может управлять им. Остальные тесты не изменялись.

Ручные API-запросы выполнены в транзакции с последующим откатом, без сохранённых проверочных скриптов:

- Категория «Каталог и спецификации»: HTTP 200, подразделение «Проектирование», получатель «Ответственный за номенклатуру»; регистрация без переопределения назначила `manager-3`.
- Ручной получатель: HTTP 201, выбранный руководитель и требуемое событие в журнале. Выбор сотрудника, отсутствующего пользователя и руководителя в отпуске — 422 с понятным сообщением.
- Руководитель закупок: чтение и наличие внешнего назначения своего сотрудника в реестре подтверждены; изменение статуса и комментарий — 403.
- Администратор: полная карточка — 200; переназначение — 200; изменение статуса — 403. Аналитика возвращает `companyScope=true`; зарождающиеся проблемы и локальный поиск — 200. Сводка проверена с `LLM_PROVIDER=none`, результат по правилам — 200.

Реальных вызовов Gemini: **0**. Изменения этапа не закоммичены. Проверочные обращения, назначения и временное изменение отпуска откатились. Браузерная приёмка не выполнялась; mock-сборку требуется повторить вне ограниченной среды.

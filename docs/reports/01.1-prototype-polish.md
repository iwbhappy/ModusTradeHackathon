# Этап 1.1 · Доработка UI-прототипа

Выполнены доработки из `docs/specs/01.1-prototype-polish.md`. Новые экраны и функции за пределами ТЗ не добавлялись. Бэкенд и внешние AI-сервисы не подключались. Этап 1 ранее принят оркестратором в браузере.

## Читаемость и структура

Добавлены Prettier и `npm run format`. Конфигурация: `printWidth: 100`, одинарные кавычки, точки с запятой, окончания строк LF. Отформатирован весь `frontend/src`, включая CSS и JSON.

API разделён по назначению:

- `api/storage.ts` — загрузка и сохранение демо, доступ, события, справочники и сброс.
- `api/tickets.ts` — создание, чтение и обработка обращений, обсуждения и присоединение.
- `api/routing.ts` — выбор ответственного, правила, резерв и отпуск.
- `api/analytics.ts` — расчёт метрик.
- `api/ai.ts` — поиск похожих, структуратор и черновики; `search-scoring.ts` — нормализация и скоринг.
- `api/index.ts` — прежние публичные импорты для экранов.

Общие UI-компоненты вынесены из `ui.tsx` в `components/ui/`. Верхняя панель и сайдбар находятся в `components/layout/`. Крупные экраны разделены на компоненты формы, карточки, очереди и аналитики в соответствующих подпапках `pages/`. Административные экраны разделены на `RoutingPage.tsx` и `UsersPage.tsx`.

Самый большой TSX-файл после форматирования — `TicketList.tsx`, 213 строк. Следующие по размеру: `RoutingPage.tsx` — 203, `TicketActions.tsx` — 186. Строк длиннее 140 символов вне литералов датасета нет. Длинными оставлены только сами тексты ситуаций, результатов, отказов и деловых реплик в данных.

При выделении компонентов сохранено состояние черновика ответа и других действий во время обновления карточки: повторное чтение обращения не размонтирует уже открытую карточку. Маршруты, роли, ограничения доступа и сквозные операции сохранены.

## Данные

S-001…S-040 написаны как 40 отдельных записей в `data/synthetic/`: закупки и склад, проектирование, сервис и ПНР, внутренние операции. Заголовки и тексты больше не собираются из общей фразы и суффиксов. Темы включают СКУД, видеонаблюдение, ОПС, совместимость аналогов, лицензии, резерв, комплектацию, отгрузку, схемы для ПНР, передачу в эксплуатацию, договоры и закрывающие документы, обучение и повторный ввод между CRM и учётной системой.

У каждого реализованного синтетического обращения свой конкретный результат. У четырёх отклонённых предложений разные причины: риск неликвидного запаса, непроверенная совместимость, открытое хранение паролей и преждевременное закрытие этапа без акта. Комментарии написаны отдельно для каждой ситуации; история содержит эти реплики без дублирования вопросов и возвратов.

Все исходные поля A-001…A-020 сохранены: ID, текст, тип, категория, автор, приоритет, статус и ответственный. Prettier добавил только завершающий перевод строки в `originals.json`. Для исходных обращений пересчитаны дополнительные демонстрационные даты; тексты исходных результатов и отказа сохранены.

Генерация оставлена только для служебного обогащения: относительных дат, SLA, стандартных событий и оценок времени. Сами 40 рабочих ситуаций, их статусы, маршруты, результаты и переписка заданы явно.

Ключ хранилища изменён с `signal-demo-v1` на **`signal-demo-v2`**, версия данных — **2**. Старый набор не загружается. Пользователи, уже открывавшие приложение, получают новый набор без ручного удаления localStorage.

## Заголовки

В форме есть необязательное поле «Кратко о сути» с ограничением 80 символов и счётчиком. Ограничение проверяется и в API. Структуратор предлагает заголовок вместе с остальными полями; принятую формулировку можно редактировать.

Без пользовательского заголовка берётся первое предложение. Если оно длинное, функция `lib/title.ts` собирает целые слова в пределах лимита и добавляет многоточие. Вручную получен, например, заголовок длиной 75 символов:

> В заявках на закупку часто нет назначения изделия и параметров, приходится…

В таблице остаётся визуальное сокращение через CSS ellipsis, а ссылка имеет `title` с полным заголовком. В карточке заголовок отображается полностью и переносится по ширине.

## Поиск похожих: ручные примеры

Скоринг использует стоп-слова, приведение к нижнему регистру, «ё → е», простые основы слов и усечение окончаний. IDF считается по всему корпусу из 60 обращений. Совпадение в заголовке весит в три раза больше совпадения в основном тексте; учитывается длина документа. За совпадение выбранной категории и подразделения добавляются бонусы. В выдачу входят открытые обращения минимум с двумя совпавшими терминами; интерфейс показывает до четырёх результатов и короткое объяснение.

Проверка выполнена вручную отдельными вызовами существующей функции `findSimilar` в интерактивной Node REPL после сброса данных. Проверочные программы, утверждения, тестовые файлы и тестовые харнессы не создавались. Вызовы использовали тот же собранный модуль API, который импортируют экраны.

| Текст | Категория / подразделение в форме | Первый результат |
| --- | --- | --- |
| В заявках на закупку часто нет назначения изделия и параметров, приходится уточнять у проектировщиков по несколько раз | Межотдельное взаимодействие / Закупки | **A-001 — Неполные параметры в заявках на оборудование** |
| В спецификации встречаются разные обозначения одного изделия. Проверка занимает время, нужна актуальная карточка позиции. | Каталог и данные / Проектирование | **A-003 — Разные обозначения одного изделия** |
| После согласования КП повторно переношу состав комплекта и количество из CRM в учётную систему, склад находит расхождения. | Интеграции и IT / IT-разработка | **S-020 — Повторный ввод состава комплекта из CRM** |
| При передаче ОПС в эксплуатацию нет общего перечня протоколов проверки, схем и документов после наладки. | Документооборот / Сервис и ПНР | **S-022 — Комплект документов при передаче ОПС в эксплуатацию** |

У A-001 объяснение в проверенной выдаче: «Совпадение: уточнение, изделия, параметры». Специальных условий для ID A-001 в алгоритме нет. Поиск повторяется после изменения текста, категории или подразделения с прежним debounce 450 мс.

Время первого ответа теперь действительно считается в рабочих часах: понедельник–пятница, 09:00–17:00 в часовом поясе браузера. Праздники не учитываются. Незавершённые обращения имеют актуальные сроки, кроме трёх явно заданных проблемных случаев; у возвратов срок обновлён.

В недельных данных виден рост подачи после запуска, затем увеличение числа реализованных. При проверке число реализаций по десяти отображаемым неделям составило **0, 0, 2, 1, 1, 5, 4, 5, 9, 3**. Последняя неделя неполная, что подписано под графиком. После будущего сброса календарные подписи сдвинутся относительно даты запуска демо.

## Аналитика

«По категориям» показывает топ-7 и агрегат «Прочие (N)», где N — число остальных категорий. Нажатие раскрывает полный список с количеством и долей каждой; повторное нажатие сворачивает его. Суммы и проценты считаются по всей выбранной выборке.

Недельный график имеет высоту **260 px**, четыре деления Y и подписи осей **11 px**. `ResizeObserver` подстраивает ширину SVG viewBox под реальную ширину контейнера: размер текста не уменьшается вместе с масштабом картинки. Подсказка показывает начало недели и обе серии при наведении или клавиатурном фокусе; нулевые столбцы тоже доступны для просмотра.

Для контентной области 1100–1700 px сетки используют `minmax(0, …)`, график меняет внутреннюю геометрию по ширине контейнера, категории переносятся в своих колонках, раскрытие «Прочих» не растягивает соседние панели. Структура и расчёт размеров проверены по коду. **Повторная визуальная проверка в браузере в этой сессии не выполнялась: браузерный инструмент недоступен.** Проверку новых tooltip, раскрытия и обоих краёв диапазона ширины следует включить в браузерную приёмку оркестратора.
